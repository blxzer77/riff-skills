# Evidence to check

Check these at decision time; versions and support facts age.

## Official sources first

1. Documentation for the exact release line and supported runtimes.
2. Release notes and security advisory channel.
3. License and dependency policy.
4. Migration, export, backup, and downgrade documentation.
5. Issue tracker or repository activity for maintenance signals.

Treat third-party posts and rankings as leads, not proof. Record the URL, claim, and
UTC date checked. If a source conflicts with another, report the conflict instead of
averaging it away.

## Maintenance signals

No single signal proves health. Look for a recent stable release, a documented
support policy, responsive issue handling, multiple maintainers, and compatibility
with the project's runtime. A high commit count can mean churn; a quiet mature
project can be healthy. Explain which interpretation applies.

## Lock-in questions

- Can data and configuration be exported in a usable format?
- Is the integration behind a small interface owned by the application?
- Are public contracts using a portable protocol or provider-specific features?
- What is the last-resort migration sequence and its downtime/data-loss risk?
- Can the dependency be removed without changing domain logic?

Never infer license, security, pricing, or support terms from memory.
